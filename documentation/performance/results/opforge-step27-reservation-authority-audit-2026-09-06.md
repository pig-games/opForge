# Reservation authority audit — prerequisite to Step 28

At integration commit `966c4f3d0fd4324e6219b5703e8cf08ac6f7c434`, the Step 27 pre-edit audit disproved the assumption that native D3 was already a reservation byte extent. `opasm_assembly_driver.asm` reads only operand 2 and advances that count; it does not multiply by operand 1. Rust `line.rs::res_directive_ast` resolves byte, active CPU word size, long or a numeric expression, checks unit multiplication, and validates the resulting span against the active CPU maximum address.

The Rust CPU registry supplies `native_word_size_bytes` and `max_program_address`. The serialized `CpuDescriptor` carries only identity/family/dialect/alias fields, and native `tkpkg_pipeline.asm::stageCpuEntryV1` stages those strings only. There is no authoritative native accessor for the missing properties. All current built-in handlers using a two-byte word does not justify a generic constant: the registry's nonstandard CPU test explicitly has three-byte words and maximum address `0x01FFFFFF`.

The zero-storage listing transport is mechanically feasible: engine execution calls BeginStatementOutput, emission, EndStatementOutput, then the driver's advance callback. Retaining a checked reservation extent after End avoids its overwrite; ordinary emitted-byte getters must keep returning zero for reservations. This does not solve the missing extent authority.

No production changes or emulator runs were made during this audit. Two independent audits agree that certifying only byte reservations would leave the planned semantics unproven. The plan therefore inserts Step 27 CPU execution-property transport, then Step 28 checked reservation semantics and listing retention. Later symbol and generated-output footer debt, all corpus failures and Phase A closure remain open. The proposed transport must keep missing metadata explicit and stage properties once per CPU selection, avoiding guessed values and per-opcode work.

Performance contribution: this audit prevents retaining an incorrect byte count; no runtime gain is measured. Total Phase A runtime gain remains unmeasured without a matched initial/current benchmark. The previously verified source-read reduction of 1,608 to 8 DOS calls is a separate scoped mechanism result, not a cumulative runtime percentage.

## Concrete prerequisite design

The audited compatible candidate is optional `CPEX` version 1. Both existing TOC readers ignore unknown bounded chunks; older readers therefore ignore these properties and cannot provide the new guarantee. New readers keep old packages loadable for unrelated operations while exposing property absence explicitly.

Proposed little-endian payload: `u16 version=1`, `u16 reserved=0`, `u32 canonical_cpu_count`, then each canonical record as `u32 id_length`, UTF-8 CPU id bytes, `u32 word_size_bytes`, `u32 max_program_address`. Require nonempty canonical ids, unique normalized keys, nonzero word size, exact canonical CPUS coverage when CPEX is present, no alias-owned records, and no trailing bytes. Absent and present-but-invalid data must remain distinct. Alias resolution precedes property selection. Confirm this exact wire contract in implementation review before codec edits.

Rust ownership: `opforge-types/src/hierarchy.rs` defines the neutral property record; `opforge-package` encodes/decodes and validates it; the registry-to-package builder in `opforge-vm/src/builder.rs` extracts authoritative handler values once per canonical CPU. Typed accessors must resolve the package's canonical CPU record without falling back to registry defaults for missing package metadata.

Native ownership: package-loader locators and buffers retain CPEX presence; pipeline selection validates and stages the matching canonical record, then commits properties atomically with the selected CPU. Preserve the existing selection failure contract while preventing a mixture of old CPU identity and new properties. Reset/package reload clears presence and values. Proposed getters return D0=0/D1=value on success and D0=1 for missing properties or no valid active selection. Do not confuse maximum address zero with missing metadata.

A complete native loader/selection harness should decode the same case package used by its live Rust oracle, select an alias of a three-byte-word CPU with max address $01FFFFFF, switch to a two-byte-word CPU with max $FFFF, and prove both values change together. A legacy package must remain loadable but fail an explicit property request. Keep malformed package rejection and required negative guest exits separate from positive exact-output parity. No permanent CPU-name table, opcode dispatch, per-statement storage or RES consumer changes belong to this prerequisite.
