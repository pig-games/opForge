# Review Report

## Scope

Full 68000-family assembler implementation, with special focus on the recently
added 68010, 68020, 68030, and 68040 CPU support. Review covers:

- `crates/opforge-families/src/m68000.rs` and `m68000/`
- `crates/opforge-families/src/m68k.rs` and `m68k/` (handler, module, operand, table)
- `crates/opforge-families/src/m68010.rs` and `m68010/`
- `crates/opforge-families/src/m68020.rs` and `m68020/`
- `crates/opforge-families/src/m68030.rs` and `m68030/`
- `crates/opforge-families/src/m68040.rs` and `m68040/`

Focus areas: instruction encoding correctness, family delegation chain integrity,
register and operand validation, and diagnostic quality for unsupported usage.

Three reviewer models (GPT-5.4, Claude Opus 4.6, Gemini 3.1 Pro) contributed
candidate findings. All findings below were code-verified by the adjudicator.

## Findings

### RVW-2026-03-29-001

- Severity: critical
- File: `crates/opforge-families/src/m68k/handler.rs`, lines 3268, 3292, 3343
- Issue: Word-sized branches (`.W` and auto-size) compute displacement as
  `target − (current_address + 4)`; long branches use `target − (current_address + 6)`.
  The M68k architecture always advances PC by 2 (past the opcode word) before adding
  the displacement, regardless of instruction length. Both DBcc (line 3404) and `.B`
  branches (line 3238) correctly use `current_address + 2`. The three word/long forms
  do not, producing displacements that are 2 bytes (`.W`) or 4 bytes (`.L`) short of
  the intended target on real hardware.
- Why it matters: Every word and long branch in every assembled program lands before
  its intended target. This is a fundamental code-generation correctness failure for the
  most common branch forms. The existing integration tests encode the same wrong
  displacements in their expected values, masking the bug.
- Fix direction: Change the `.W`, auto-size, and `.L` branch displacement calculations
  to use `current_address + 2` uniformly, matching the byte and DBcc cases. Update all
  corresponding test expected byte values to match hardware-correct displacements.

### RVW-2026-03-29-002

- Severity: critical
- File: `crates/opforge-families/src/m68k/handler.rs`, line 2800
- Issue: `encode_long_data_register_multiply` always sets bit 10 of the extension word
  (`| (1 << 10)`), selecting the 32×32→64 product form, and leaves bits [2:0] as zero
  (Dh = D0). For a single-register `MULS.L <ea>, Dn` or `MULU.L <ea>, Dn` (the 32-bit
  result form), the M68020 PRM requires bit 10 = 0 (32-bit form) and bits [2:0] = Dl
  (i.e., Dh = Dl). With the current encoding the hardware executes a 64-bit multiply
  and writes the high 32 bits into D0, regardless of the specified destination register.
- Why it matters: `MULS.L <ea>, D1` through `MULS.L <ea>, D7` silently clobber D0 at
  runtime. Only `MULS.L <ea>, D0` coincidentally produces the expected 32-bit result.
  This is a register-aliasing data-corruption bug on every long multiply where the
  destination is not D0.
- Fix direction: Remove `| (1 << 10)` and OR in `dst_reg as u16` for bits [2:0] so that
  Dh = Dl (bit 10 = 0, 32-bit result form). Update test expectations accordingly.

### RVW-2026-03-29-003

- Severity: high
- File: `crates/opforge-families/src/m68k/handler.rs`, lines 5240–5244
- Issue: `encode_absolute_long` rejects any address above `MAX_M68000_ABSOLUTE_ADDRESS`
  (`0x00FFFFFF`). This constant is the 68000's 24-bit bus limit. The 68020, 68030, and
  68040 have 32-bit address buses, but none of their handlers override this static
  method. Identically, `encode_absolute_word` applies the 24-bit mask before the
  sign-extension check, so 68020+ programs using the upper 32-bit address space via `.W`
  absolute (e.g., `($FFFF8000).W`) are also rejected.
- Why it matters: Any 68020/030/040 program addressing memory above 16 MB is rejected
  with "68000 absolute .L address out of 24-bit range" even though the target CPU
  supports a full 32-bit address space. This blocks ROM and MMIO mappings above 16 MB,
  which are normal in 68020+ systems.
- Fix direction: Convert `encode_absolute_long` and `encode_absolute_word` from static
  functions to methods parameterized by address bus width (or overridable by the CPU
  handler), and supply 32-bit limits in `M68020CpuHandler`, `M68030CpuHandler`, and
  `M68040CpuHandler`.

### RVW-2026-03-29-004

- Severity: high
- File: `crates/opforge-families/src/m68020/handler.rs`, line 256
- Issue: `M68020CpuHandler::encode_instruction` explicitly returns `EncodeResult::NotFound`
  for `M68010MnemonicKind::Bkpt` and `M68010MnemonicKind::Rtd`. `M68030CpuHandler` and
  `M68040CpuHandler` delegate entirely to `M68020CpuHandler` for m68010 mnemonics, so
  both instructions are unreachable on all three later CPUs. `supports_mnemonic` for
  m68020+ also excludes them.
- Why it matters: `BKPT #n` and `RTD #d16` are documented as valid on the 68010 and
  all later 68k processors. Users targeting m68020, m68030, or m68040 receive an
  "unknown instruction" error for both instructions, with no hint that the CPU supports
  them. The LSP completion layer also excludes them.
- Fix direction: In `M68020CpuHandler::encode_instruction`, route `Bkpt` to the family
  handler's BKPT encoder and `Rtd` to the family handler's RTD encoder (the same
  delegations the m68010 handler uses). Add both to `M68020CpuHandler::supports_mnemonic`.

### RVW-2026-03-29-005

- Severity: high
- File: `crates/opforge-families/src/m68010/handler.rs`, lines 55–93, 376–383;
  `crates/opforge-families/src/m68020/handler.rs`
- Issue: `MOVE CCR,<ea>` (the 68010+ form that reads the CCR into a memory operand) is
  implemented only in `M68010CpuHandler` via `encode_move_from_ccr`. The family handler
  returns `EncodeResult::NotFound` when CCR is the MOVE source (line 1619–1622 of
  `m68k/handler.rs`). `M68020CpuHandler` does not intercept the CCR-source MOVE form
  before delegating to the family handler, so the instruction fails on m68020, m68030,
  and m68040 with "unknown instruction". `M68030CpuHandler` and `M68040CpuHandler`
  inherit the same gap through m68020.
- Why it matters: `MOVE CCR,<ea>` is a valid instruction on all 68010+ processors. The
  68010 handler implements it correctly; the three later families silently drop it,
  breaking ISA fidelity for a documented carry-forward instruction.
- Fix direction: Add the same `MOVE CCR,<ea>` interception (`encode_move_from_ccr`
  delegation) to `M68020CpuHandler::encode_instruction` that `M68010CpuHandler` uses.
  `M68030CpuHandler` and `M68040CpuHandler` will inherit it through m68020.

### RVW-2026-03-29-006

- Severity: medium
- File: `crates/opforge-families/src/m68k/handler.rs`, lines 2814–2816
- Issue: `encode_chk` returns `EncodeResult::error("CHK does not support .L size on
  baseline 68000")` for the `.L` size suffix. Because the family handler is tried after
  the CPU handler returns `NotFound`, this hard Error prevents the 68020+ CPU handler
  from ever intercepting `CHK.L`. `CHK.L` is a valid 68020 instruction.
- Why it matters: Users targeting m68020/030/040 receive a hard error referencing
  "baseline 68000" even when the target CPU supports the instruction, with no path for
  the CPU handler to override the family's rejection.
- Fix direction: Change `encode_chk` to return `EncodeResult::NotFound` for `.L` size
  (not `Error`). Then add explicit `CHK.L` handling in `M68020CpuHandler::encode_instruction`
  (opcode base `0x4100 | (Dn<<9) | EA`). The 68000 error message would then only appear
  when the 68000 CPU handler's own check fires.

### RVW-2026-03-29-007

- Severity: medium
- File: `crates/opforge-families/src/m68k/operand.rs`, lines 38–46;
  `crates/opforge-families/src/m68k/handler.rs`, lines 124–130;
  `crates/opforge-families/src/m68040/handler.rs`, lines 52–61
- Issue: The `ControlRegisterKind` enum contains only SFC, DFC, VBR, CACR, CAAR, MSP,
  and ISP. The 68040 adds TC (`0x003`), ITT0 (`0x004`), ITT1 (`0x005`), DTT0 (`0x006`),
  DTT1 (`0x007`), MMUSR (`0x805`), URP (`0x806`), and SRP (`0x807`) as valid MOVEC
  target registers. None of these exist in the enum, the parser table, or the
  `M68040CpuHandler::movec_control_register_code` function. They cannot be parsed at all.
- Why it matters: Any 68040 program using MOVEC to access translation-control, address
  translation, or MMU supervisor registers fails at parse time. This removes a
  significant portion of 68040 system-programming capability.
- Fix direction: Add the eight missing variants to `ControlRegisterKind`, add their
  string names to the parser table in `handler.rs`, and map them in
  `M68040CpuHandler::movec_control_register_code` with the correct PRM register codes.

### RVW-2026-03-29-008

- Severity: medium
- File: `crates/opforge-families/src/m68010/handler.rs`, line 424
- Issue: `M68010CpuHandler::supports_mnemonic` returns `true` for all mnemonics where
  `has_m68020_mnemonic(mnemonic)` is true. The m68010 handler rejects every 68020
  mnemonic at encode time with an error ("not supported on m68010"), so `supports_mnemonic`
  misrepresents what the m68010 CPU actually accepts.
- Why it matters: LSP completion, hover documentation, and diagnostic filtering that
  rely on `supports_mnemonic` will offer BFTST, CAS, CAS2, CALLM, TRAPcc, etc. as valid
  choices on a 68010 target. Users assembling for 68010 get misleading completions.
- Fix direction: Remove the `has_m68020_mnemonic(mnemonic)` clause from
  `M68010CpuHandler::supports_mnemonic`. The m68010 legitimately supports all base 68000
  and m68010 mnemonics; it should not advertise m68020+ mnemonics.

### RVW-2026-03-29-009

- Severity: low
- File: `crates/opforge-families/src/m68010/handler.rs`, lines 212–281;
  `crates/opforge-families/src/m68k/handler.rs`, lines 5494–5557
- Issue: `M68010CpuHandler::encode_moves` is a near-identical copy of
  `M68KFamilyHandler::encode_moves_instruction`. `M68020CpuHandler` already delegates to
  `self.family.encode_moves_instruction(...)` instead of maintaining its own copy; the
  m68010 handler does not.
- Why it matters: Any bug fix or enhancement to the canonical `encode_moves_instruction`
  in the family handler must also be applied to the m68010 handler's private copy.
  Maintenance divergence is likely over time.
- Fix direction: Remove the private `encode_moves` from `M68010CpuHandler` and replace
  the call at line 418 with `self.family.encode_moves_instruction(parsed.size, operands, ctx)`,
  matching the m68020 pattern.

## Testing Gaps

1. **Branch displacement round-trip.** No test verifies that a word or long branch to
   a label at a known absolute address produces the hardware-correct displacement.
   Existing tests lock in the buggy `+4`/`+6` formula in their expected byte values.
   A test assembling `BNE.W label` with a known instruction address and label address,
   then asserting `displacement = target − (instr_addr + 2)`, is required.

2. **MULS.L/MULU.L register alias.** No test asserts that `MULS.L <ea>, D2` encodes
   Dh = D2 (bits [2:0] of the extension word = 2) and bit 10 = 0. A test comparing
   the extension word against a hardware-reference value for each destination register
   would catch the current corruption.

3. **BKPT, RTD, and MOVE CCR on 68020/030/040.** No positive encoding tests exist
   for these carry-forward instructions on m68020, m68030, or m68040 targets.

4. **CHK.L on 68020+.** No positive test for `CHK.L <ea>, Dn` on any later-family CPU.

5. **Absolute addresses above 16 MB on 68020/030/040.** No test exercises an absolute
   `.L` or `.W` address above `0x00FFFFFF` on a 68020+ target.

6. **68040 MOVEC with MMU/translation control registers.** No test attempts
   `MOVEC TC, D0` or any ITT/DTT/URP/SRP/MMUSR variant on an m68040 target.

7. **Per-CPU-handler unit tests absent.** None of the CPU-specific handler files
   (`m68000/handler.rs`, `m68010/handler.rs`, `m68020/handler.rs`, `m68030/handler.rs`,
   `m68040/handler.rs`) contain inline `#[cfg(test)]` modules. All validation goes
   through cross-crate integration tests, making it harder to isolate encoding edge cases.

## Residual Risks

1. **Long divide not implemented on 68020+.** `DIVS.L` and `DIVU.L` (32-bit quotient
   and remainder forms using extension words, valid from 68020 onward) are not handled
   by the 68020 CPU handler. The family handler's hard error for `.L` DIVS/DIVU
   (the same pattern as CHK.L in finding RVW-2026-03-29-006) blocks any CPU override.
   This was not elevated to a primary finding because it follows the same root cause as
   finding 006, but it represents a separate instruction gap.

2. **MOVES EA validation.** `encode_moves_instruction` accepts any memory-alterable EA
   without checking that PC-relative modes (which are not valid for MOVES) are excluded.
   The M68020 PRM prohibits `MOVES` with PC-relative addressing; this is not currently
   caught.

3. **CAS2 register field validation.** `encode_cas2_instruction` passes both indirect
   operands through `general_register_descriptor`, which accepts data or address
   registers. Per the M68020 PRM the Rn fields in CAS2's extension words must be address
   registers. A data register in that position is silently accepted and produces incorrect
   machine code.

4. **68030/040 MMU instruction set absent.** The 68030 and 68040 each have a PMMU
   instruction set (PMOVE, PLOAD, PSTORE, PFLUSHA, PFLUSHN, PTEST, etc.) that neither
   handler makes any attempt to implement. Programs using 68030/040 MMU instructions
   receive "unknown instruction" with no diagnostic indicating that the instruction
   family is not yet supported.

5. **Multi-pass branch displacement masking.** On pass 1, unresolved branch targets
   use a placeholder displacement of 0, which can cause the assembler to incorrectly
   select the `.B` form when the full displacement requires `.W`. The existing
   pass-splitting and retry logic may mitigate this, but the interaction with the
   incorrect `.W` displacement formula (finding RVW-2026-03-29-001) increases the risk
   of silent wrong-size selection in multi-pass scenarios.

## Brief Summary

Two critical code-generation bugs affect every assembled program targeting any member
of the 68000 family. First, word-sized and long-sized branch displacements are
systematically off by 2 or 4 bytes because the displacement formula uses the full
instruction length rather than the fixed +2 advance the M68k architecture specifies;
only the `.B` and DBcc forms are correct. Second, `MULS.L`/`MULU.L` always encodes
the 64-bit result form with D0 as the implicit high register, corrupting D0 on every
long multiply where the destination is D1–D7.

Three high-severity findings cover the 68010–68040 lineage specifically: the 24-bit
absolute address cap inherited from the base handler is never relaxed for the 32-bit
later CPUs; BKPT and RTD are explicitly dropped at the m68020 delegation boundary and
never re-added; and MOVE CCR,<ea> (a 68010 carry-forward instruction) is present in
the m68010 handler but absent from the m68020/030/040 chain.

At medium severity: CHK.L returns a hard error from the family handler that blocks the
68020+ CPU handlers from ever seeing the instruction; the 68040's MMU control registers
(TC, ITT0/1, DTT0/1, URP, SRP, MMUSR) do not exist in the parser or enum and cannot
be assembled; and the m68010 handler incorrectly advertises all 68020+ mnemonics as
supported.

The test suite consistently validates the existing (incorrect) encodings in its expected
values, which is why the critical displacement and multiply bugs have not been caught.
Hardware-verified round-trip tests against known-good displacements and extension words
are the highest-priority testing addition.
