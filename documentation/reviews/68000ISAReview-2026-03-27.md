# Review Report

## Scope

Full worktree review of current Motorola 68000 support, not limited to the
branch diff, focused exclusively on baseline 68000 ISA coverage and
effective-address legality.

Primary external reference: the NXP M68000 Family Programmer's Reference
Manual. The direct NXP PDF URL returned an unavailable-page response in this
environment, so the review used the Internet Archive mirror of `M68000PRM`
for the same manual content and used public 68000 reference pages only for
spot corroboration.

## Findings

### RVW-2026-03-27-001

- Severity: high
- File: `crates/opforge-families/src/m68k/handler.rs:733`, `crates/opforge-families/src/m68k/handler.rs:1788`, `crates/opforge-asm/src/tests.rs:2849`
- Issue: `CMP` is routed through the generic data-register binary helper, and
  that helper accepts `Dn,<memory alterable ea>` whenever the source is a data
  register. Baseline 68000 `CMP` is `CMP <ea>,Dn` only, so forms such as
  `CMP.W D0,(A0)` are incorrectly accepted and encoded instead of being
  rejected.
- Why it matters: this is a silent misassembly path. The emitted opcode lands
  in the memory-destination opcode space rather than a legal `CMP` encoding, so
  invalid source assembles into different machine code with no diagnostic.
- Fix direction (one direction only; resolve competing options before finalizing):
  split `CMP` off from the generic data-register binary helper so the encoder
  only accepts the legal `CMP <ea>,Dn` shape, then add negative tests for
  `CMP.B/W/L Dn,<ea>`.

### RVW-2026-03-27-002

- Severity: high
- File: `crates/opforge-families/src/m68k/handler.rs:3780`, `crates/opforge-families/src/m68k/handler.rs:3851`, `documentation/opForge-reference-manual.md:245`
- Issue: `eval_pc_relative_displacement` rebases any expression containing an
  identifier, register, or `$` as if it were a relocatable PC-relative target.
  Because the assembler language explicitly allows scalar `.const` and `.set`
  symbols in expressions, valid operands such as `foo(PC)` with `foo .const 4`
  are encoded as `(symbol_value - (PC + 2))` instead of the literal
  displacement `4`.
- Why it matters: this silently misencodes valid baseline 68000 source.
  Named scalar constants in `d16(PC)` and `d8(PC,Xn)` forms can produce the
  wrong displacement bytes without any error, which is worse than a rejection.
- Fix direction (one direction only; resolve competing options before finalizing):
  change PC-relative displacement evaluation so it subtracts `PC + 2` only for
  relocatable target expressions such as labels, and evaluates plain scalar
  symbols through the normal expression path.

### RVW-2026-03-27-003

- Severity: medium
- File: `crates/opforge-families/src/m68k/handler.rs:733`, `crates/opforge-families/src/m68k/handler.rs:2337`, `crates/opforge-families/src/m68k/handler.rs:2849`, `crates/opforge-families/src/m68k/handler.rs:3519`, `crates/opforge-families/src/m68k/handler.rs:3554`, `crates/opforge-asm/src/tests.rs:3202`, `crates/opforge-families/src/m68k/handler.rs:6361`, `examples/68000_btst_pc_relative_error.asm:1`
- Issue: `CMPI` and `BTST` use alterable-only destination legality predicates,
  so PC-relative destinations such as `CMPI.W #1,4(PC)` and `BTST #1,4(PC)`
  are rejected. The 68000 PRM defines both instructions over data-addressing
  modes, which include `d16(PC)` and `d8(PC,Xn)` for these read-only cases.
- Why it matters: this leaves a real baseline-68000 addressing-mode coverage
  gap and hard-codes the wrong legality rule into shipped tests and example
  artifacts, so legal 68000 source is diagnosed as invalid.
- Fix direction (one direction only; resolve competing options before finalizing):
  add a separate `data_addressing` predicate that includes PC-relative data
  effective addresses and use it for read-only destination instructions such as
  `CMPI` and `BTST`, while keeping `BCHG/BCLR/BSET` on alterable-only
  destinations.

## Testing Gaps

- There is no focused negative regression proving `CMP.B/W/L Dn,<ea>` is
  rejected rather than encoded.
- There is no targeted coverage for scalar `.const` or `.set` symbols used in
  `d16(PC)` and `d8(PC,Xn)` effective-address forms.
- The current suite does not maintain a manual-derived matrix that separates
  data-addressing instructions from data-alterable instructions, which allowed
  the incorrect `BTST` and `CMPI` PC-relative rule to become part of the
  shipped assertions.

## Residual Risks

- This review focused on the native assembler family handler, shipped tests,
  examples, and documentation. It did not perform exhaustive opcode
  differential testing against a second assembler or emulator.
- The direct NXP PDF was not reachable from this environment, so manual
  verification used the Internet Archive mirror and text extraction of the same
  `M68000PRM` content.
- Repository documentation still mixes the original narrow v0.1 68000 slice
  with later expansion work, so behavior claims remain somewhat harder to audit
  than a single consolidated conformance matrix would be.

## Brief Summary

Three material issues remain in the current 68000 implementation: one silent
illegal-form misassembly in `CMP`, one silent misencoding path for scalar-symbol
PC-relative displacements, and one real PC-relative addressing-mode coverage
gap for `CMPI` and `BTST`. The rest of the reviewed baseline 68000 surface
looks broadly aligned with the intended ISA slice, but these gaps mean full
baseline ISA and addressing-mode conformance is not yet complete.
